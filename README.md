# Спори карткових платежів: коли варто боротися за чарджбек

Хакатон «Основи Data Mining». Модель оцінює ймовірність виграти спір (`won`), а
економічне правило вирішує, чи витрачати $6 на representment:

> боротися, якщо **p × 0,2 × amount_usd > 6**, тобто p > p\* = 30 / amount_usd.

Score = Σ (0,2 · amount_usd · won − 6) по спорах, за які вирішили боротися;
бейзлайн — «боротися завжди».

## Результати

Поділ за часом: train — тижні 0–17, validation — 18–21, test — 22–25. Модель обрано
лише на train (вкладені часові фолди) і зафіксовано до відкриття test.

| Test, тижні 22–25 | |
|---|---|
| Обрана модель | логістична регресія, C = 0,1 |
| ROC-AUC / log loss / Brier | 0,827 / 0,332 / 0,096 |
| Score моделі | **$9 605,00** на 1 670 спорах із відомою сумою |
| «Боротися завжди» | $7 865,00 |
| Приріст | **+$1 740,00 (+22,1%)**, позитивний у кожному з 4 тижнів |
| Лише незмінені суми (1 630 спорів) | +$1 716,60 |

- Картки (PSP_B/C) виграються у 22% випадків, PayPal (PSP_A) — у 89%; причина `other` — 17%.
- CatBoost, калібрування, ансамблі, взаємодії й ваги за сумою дали на train щонайбільше
  +$68 до логістичної регресії — менше за наперед заданий допуск $257 ($50 на 1 000 спорів),
  тому протокол обрав простішу модель.
- Обмеження: у даних лише спори, за які вже боролися; це не причинна оцінка для всіх спорів.

### Друга, наперед зафіксована оцінка (ноутбук 10)

Після першої оцінки покращення розроблялися лише на тижнях 0–21 (train+validation) і вибиралися тим самим
правилом допуску; потім кожен рецепт один раз оцінено на test, перенавченим на тижнях 0–21.

| Test, тижні 22–25 | Score | Δ до «завжди» (95% bootstrap) | ROC-AUC | Log loss |
|---|---|---|---|---|
| Перша оцінка: ЛР, train 0–17 (заморожена) | $9 605,00 | +$1 740,00 | 0,827 | 0,332 |
| **Друга оцінка: ЛР, перенавчена на 0–21 (обрана наперед)** | **$9 598,00** | **+$1 733,00** [1 552; 1 907] | **0,842** | **0,326** |
| + вага свіжих тижнів | $9 610,00 | +$1 745,00 | 0,848 | 0,324 |
| + історія мерчанта | $9 612,20 | +$1 747,20 | 0,843 | 0,326 |
| + обидва | $9 608,40 | +$1 743,40 | 0,849 | 0,325 |
| CatBoost | $9 620,40 | +$1 755,40 | 0,864 | 0,309 |
| Лише правило суми (стала ймовірність) | $8 689,60 | +$824,60 | — | — |

- Усі рецепти в межах ±$22 один від одного; інтервали різниці з першою оцінкою охоплюють 0. Покращення ймовірностей
  (ROC-AUC, log loss) реальні, але гроші майже не змінюють: більшість рішень очевидні.
- Приблизно половина приросту — просте правило «не боротися за малі суми» (+$825 із +$1 740); решта — ризик
  конкретного спору: картки (+$1 068 до «завжди»), причина `other` (+$192).
- Що дорожча дія, то цінніша модель: при C = $10 приріст +$4 622, при C = $4 — +$875.
- Категорії `authorization` немає в жодній частині даних. Останній тиждень test (25) має 301 спір проти ~470 у
  попередніх — ознака можливого цензурування нерозв'язаних спорів.

## Запуск

Потрібен [uv](https://docs.astral.sh/uv/) і `dataset.csv` у корені репозиторію.
**Датасет не публікується й не комітиться** (`*.csv` у `.gitignore`).

```bash
uv sync                          # Python 3.12 і точні версії залежностей з uv.lock
uv run pytest                    # тести на реальних даних пропускаються без dataset.csv
uv run ruff check                # стиль і типові помилки
./scripts/reproduce.sh           # повне відтворення (~5 хв), включно з фінальним test
./scripts/reproduce.sh --no-test # те саме без відкриття test
```

Фінальна оцінка навмисно виконується лише один раз: повторний запуск зупиниться,
щоб test не використовувався для вибору моделі. Щоб відтворити з нуля, видаліть
теки `*_outputs/` і `outputs/`.

Ноутбуки редагуються як `.py` (формат percent); після змін —
`uv run jupytext --sync notebooks/*.py`. Виконані копії з виводами з'являються в
`build/notebooks/` і в git не потрапляють: виводи можуть містити рядки даних.
