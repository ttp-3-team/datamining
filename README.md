# Спори карткових платежів: рішення про оскарження чарджбеку

Проєкт хакатону «Основи Data Mining». Модель оцінює ймовірність p виграшу спору (`won`); рішення про оскарження
приймається за правилом рішення p × 0,2 × amount_usd > 6, тобто виграш V = 0,2 × amount_usd, вартість дії C = $6
(`data_dictionary.md`). Еквівалентно: боротися, якщо p > 30 / amount_usd.

Score — чистий дохід стратегії: Σ (0,2 × amount_usd × won − 6) за спорами, які стратегія оскаржує. Базова стратегія —
«боротися завжди». Спори без придатної USD-суми не отримують рішення (`review_amount`) і не входять до Score;
решта утворює суму, придатну для Score (`score_eligible`).

## Дані та поділ

- Вихідний файл містить 10 838 рядків; після видалення 158 повних дублікатів лишається 10 680 спорів.
- Поділ за тижнем спору: train — тижні 0–17 (7 246 спорів), validation — 18–21 (1 683), test — 22–25 (1 687);
  64 спори не мають коректного тижня.
- На test 1 670 спорів мають суму, придатну для Score; 17 — не мають.
- Категорія `authorization` відсутня в усіх частинах. Тиждень 25 містить 301 спір, тижні 22–24 — від 400 до 499.

## Метод

1. Огляд і підготовка даних: очищення, аудит USD-сум, часовий поділ (ноутбуки 01–02).
2. Перші моделі та порівняння на validation (ноутбуки 03–04).
3. Вибір стратегії лише на train вкладеною часовою перевіркою: зовнішні періоди — тижні 6–9, 10–13, 14–17;
   гіперпараметри обираються на внутрішніх зрізах попередніх тижнів (ноутбук 05). Порівнювалися логістична
   регресія (ЛР), HistGradientBoosting, CatBoost, калібрування, ансамблі, взаємодії ознак і ваги за сумою
   (ноутбуки 05–09). Складніший метод обирається, лише якщо його перевага над простішим перевищує $50 на 1 000
   оцінених спорів (`PRACTICAL_GAP_USD_PER_1000`); за цим правилом обрано ЛР.
4. Перша оцінка: обраний рецепт (ЛР, C = 0,1, навчання на тижнях 0–17) зафіксовано до відкриття test і оцінено
   один раз (`disputes.final_test_evaluation`).
5. Друга оцінка: рецепти розроблено й обрано на тижнях 0–21 тією самою вкладеною часовою перевіркою; обраний
   рецепт (ЛР, перенавчена на тижнях 0–21) зафіксовано до оцінювання test. Інші рецепти оцінено на test для
   порівняння (ноутбук 10, `disputes.second_evaluation`).

Протоколи кожного етапу фіксуються до читання даних; контроль доступу забороняє читати таблиці, не заявлені
в протоколі (зокрема test до фінальних етапів).

## Відтворення

Потрібні [uv](https://docs.astral.sh/uv/) і `dataset.csv` у корені репозиторію.

```bash
uv sync                          # Python 3.12 і зафіксовані версії залежностей (uv.lock)
uv run pytest                    # тести на реальних даних пропускаються без dataset.csv
uv run ruff check
./scripts/reproduce.sh           # повне відтворення, включно з обома оцінками на test
./scripts/reproduce.sh --no-test # без звернення до test
```

Кожна оцінка на test виконується один раз: повторний запуск за наявних результатів зупиняється. Для відтворення
з нуля попередньо видаліть результати:

```bash
rm -rf outputs model_outputs comparison_outputs *_outputs final_test_outputs_v2 build catboost_info
```

Ноутбуки редагуються як `.py` (формат percent); `.ipynb` генеруються командою
`uv run jupytext --to ipynb notebooks/*.py`. Виконані копії з виводами зберігаються в `build/notebooks/`
і не додаються до git.

## Конфіденційність даних

Датасет не публікується й не додається до репозиторію: `*.csv`, теки результатів і `build/` внесено до
`.gitignore`. Ноутбуки зберігаються без виводів, оскільки виводи можуть містити рядки даних. Звіти оцінок на test
містять лише агреговані показники.

## Обмеження

- Дані містять лише спори, які оскаржувалися й отримали результат; оцінки не поширюються на всі спори
  (вибірковість).
- Дата появи мітки `won` невідома; часові схеми припускають, що результати попередніх тижнів доступні на момент
  навчання.
- Агреговані результати першої оцінки були відомі до фіксації протоколу другої оцінки.
- PSP повністю визначає спосіб оплати, тому їхні ефекти не розділяються.
